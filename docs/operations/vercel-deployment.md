# Vercel Deployment (full stack)

This deployment runs the whole application in one Vercel project:

| Component | Vercel primitive | Source |
|---|---|---|
| Next.js UI | Service (Next.js runtime) | `frontend/` |
| FastAPI API | Service (container runtime) | `backend/Dockerfile.vercel` |
| Celery ingestion worker | *Not deployed* — inline fallback | n/a |
| Document files | Vercel Blob (private store) | browser → Blob → FastAPI finalize |
| Postgres / Redis / Qdrant | External providers | configured by environment variables |

Root [`vercel.json`](../../vercel.json) owns public routing. `/api/v1/*` goes to
the backend service; everything else goes to the frontend. The frontend's
`/api/blob/token` route is served by Next.js and uses a private service binding
to authenticate callers against FastAPI before minting a Blob upload URL.

The project's stable free URL is **https://fikra-ai-kappa.vercel.app**
(the shorter `fikra-ai.vercel.app` was already taken). A production deploy also
exposes a deployment-specific `*.vercel.app` URL in the CLI output; always use
the stable project URL for links and CORS. For a custom domain, add it under
Project Settings → Domains and include it in `ALLOWED_ORIGINS`.

## 1. Free-plan limits you must accept

The Hobby plan can host this app, but with tight limits:

- Functions: 2 GB memory, 300 s maximum duration, 4.5 MB request bodies.
  Client-direct Blob uploads avoid the body limit.
- No daemon is deployed (the Celery worker was removed from the Vercel project
  in favour of the built-in inline ingestion fallback). If you ever want the
  daemon back, re-add it to the `daemons` key in the root `vercel.json` and
  re-check the quota below.
- Python function bundle limit is 500 MB; the container runtime is used for the
  backend so Tesseract, Poppler and libmagic are available.

The API container runs the FastAPI service only; ingestion tasks are processed
inline by the API process when no Celery worker is present (see
`celery_unavailable_processing_inline` in `app/api/v1/documents.py`).

## 2. External services

Vercel has no persistent filesystem, so provision:

- **Postgres** (Neon free tier works). Set `DATABASE_SSL=true`,
  `DATABASE_POOL_SIZE=5`, `DATABASE_MAX_OVERFLOW=5` to stay under connection caps.
- **Redis** that supports the Redis wire protocol and blocking list commands
  (`BLPOP`). Celery cannot use an HTTP-only REST endpoint such as Upstash's
  REST API. Use a Redis provider with TCP/TLS support.
- **Qdrant Cloud** (or any reachable Qdrant). Set `QDRANT_URL`,
  `QDRANT_API_KEY`, `QDRANT_COLLECTION`.
- **Groq API key** for the LLM.

## 3. Create and connect the Blob store

```powershell
npx vercel@latest link
npx vercel@latest blob create-store documents --access private --yes
```

The connection injects `BLOB_STORE_ID` and a rotating `VERCEL_OIDC_TOKEN` into
every service. Both the Python SDK (backend/worker) and `@vercel/blob`
(frontend token route) use these automatically; no long-lived
`BLOB_READ_WRITE_TOKEN` is required. The CLI also adds one because it is handy
for local development and for issuing browser tokens outside Vercel. If you
need local Blob development, add the Development environment in the store's
Project Connection settings and run `npx vercel@latest env pull`.

Keep `BLOB_ACCESS=private`. Downloads remain authenticated through
`GET /api/v1/documents/{id}/download`.

## 4. Environment variables

Set these on the Vercel project (Production, and Preview/Development as needed).
Secrets belong in Vercel, never in `vercel.json` or Git.

```text
APP_ENV=production
DEBUG=false
SECRET_KEY=<openssl rand -hex 64>
JWT_SECRET_KEY=<openssl rand -hex 64>
# Must be a valid JSON array: pydantic-settings json.loads()es list[str] env
# values before field validation. See the note below on setting it via the API.
ALLOWED_ORIGINS=["https://<your-project>.vercel.app"]

DATABASE_URL=postgresql+asyncpg://<user>:<password>@<host>/<db>
DATABASE_SSL=true
DATABASE_POOL_SIZE=5
DATABASE_MAX_OVERFLOW=5

# Redis Cloud's free tier only exposes DB 0. Keep all three on the same DB;
# key namespaces (ratelimit:*, Celery queues/results) do not collide.
REDIS_URL=rediss://<host>:<port>/0
CELERY_BROKER_URL=rediss://<host>:<port>/0
CELERY_RESULT_BACKEND=rediss://<host>:<port>/0

GROQ_API_KEY=<groq key>
QDRANT_URL=https://<cluster>.<region>.aws.cloud.qdrant.io
QDRANT_API_KEY=<qdrant key>
QDRANT_COLLECTION=fikra-ai

STORAGE_BACKEND=vercel_blob
BLOB_ACCESS=private
NEXT_PUBLIC_UPLOAD_MODE=blob
```

`BLOB_STORE_ID`, `VERCEL_OIDC_TOKEN` and (when added by the CLI/dashboard)
`BLOB_READ_WRITE_TOKEN` are added by the Blob store connection; do not duplicate
them manually unless you are deploying outside Vercel. `BACKEND_INTERNAL_URL`
is generated by the service binding in `vercel.json`; do not set it.

**Setting `ALLOWED_ORIGINS`:** `vercel env add --value '["https://..."]'`
strips the double quotes and stores `[https://...]`, which makes both the API
and the Celery daemon crash at import with `JSONDecodeError`. Set this one
variable through the Vercel REST API so the quotes survive:

```powershell
# Find the env var id (prints keys/ids only, never values)
npx vercel api /v9/projects/<project>/env --raw |
  python -c "import sys,json; d=json.load(sys.stdin); print([(x['key'],x['id']) for x in d['envs'] if x['key']=='ALLOWED_ORIGINS'])"

# payload.json: {"value":"[\"https://<your-project>.vercel.app\"]"}
npx vercel api /v9/projects/<project>/env/<id> -X PATCH --input payload.json

npx vercel deploy --prod   # redeploy so the change reaches the services
```

The config validator also tolerates a quote-stripped `[https://a, https://b]`
value, but pydantic-settings 2.3.4 decodes `list[str]` env values first, so the
stored value must still be valid JSON.

If 2 GB functions run out of memory during retrieval, set
`RERANKER_ENABLED=false`. Retrieval then uses vector ordering only.

## 5. Migrations before the first deploy

Migrations are a release step, not a request-time action:

```powershell
npx vercel@latest env pull .env.vercel
cd backend
..\.venv\Scripts\alembic.exe upgrade head
```

`alembic.ini` reads `DATABASE_URL` from the environment/CWD. Do not commit
`.env.vercel`. For automation, run the same command in CI with `DATABASE_URL`
supplied as a secret. Migrations are not rolled back by a Vercel rollback.

## 6. Deploy

Connect the Git repository in the Vercel dashboard (push to `main` deploys
Production), or deploy manually:

```powershell
npx vercel@latest deploy --prod
```

The root `vercel.json` is required. `frontend/vercel.json` is a service-local
fallback for standalone frontend builds; it must not contain a catch-all API
rewrite because `/api/blob/token` is a Next.js route handler.

## 7. Verify

1. `GET https://<domain>/api/v1/health/live` → `200`.
2. `GET https://<domain>/api/v1/health/ready` → `200` (DB, Redis, Qdrant, models).
3. Log in, upload a small PDF, and watch it reach `READY`.
4. No worker/daemon to inspect (this deployment runs without Celery; ingestion
   falls back to inline processing).
5. In the Blob store dashboard, confirm an object under `uploads/`.

## 8. Rollback and recovery

Use Vercel's instant rollback for the deployment. Database migrations are not
reversed — write forward-compatible migrations. If a bad migration has already
run, restore Postgres from backup before redeploying the previous image
(see [Backup and Restore](backup-and-restore.md)).

## 9. Local development is unchanged

`npm run dev` in `frontend/` still proxies `/api/v1/*` to `localhost:8000`, and
`STORAGE_BACKEND=local` keeps uploads on disk. Only set
`NEXT_PUBLIC_UPLOAD_MODE=blob` locally if you have pulled Vercel Blob
credentials and want to test the client-direct path.
